Topic A — Conditional Form Elements (10 pts)
What to show on screen:
Open Petition2.html and Petition2.js side by side. Point to handleSignerTypeChange() and the conditional section divs in the HTML.
The "why" to talk through:
The conditional sections all exist in the HTML from the start — they're just hidden. Each one has the class conditional-section, and in the CSS that class has display: none. When the user picks a signer type, the JS function handleSignerTypeChange() fires. It first loops through all sections and strips the visible class from them (so switching types cleans up the previous one), then adds visible only to the matching section. In the CSS, .conditional-section.visible sets display: block — that's the only thing making them appear and disappear. The JS never directly touches display — it just manages classes, and CSS does the visual work.
Alternative technique to research:

"Instead of toggling a CSS class, you could manipulate element.style.display directly in JavaScript — setting it to 'block' to show and 'none' to hide."

Justify your choice:
The CSS class approach is cleaner because the styling logic stays in CSS where it belongs. If you ever want to add a transition or animation to the reveal, you just update the CSS — you don't touch the JS. Direct style manipulation mixes presentation into your logic, which gets messy.
Demo trick — live fix:
In Petition2.css, find .conditional-section and temporarily change display: none to display: block. Save and refresh — all sub-sections will be visible at once, which looks broken. Topic B — Adding Rows Dynamically (10 pts)
What to show on screen:
Point to addTableRow() in Petition2.js and show getElementById("signaturesBody") in the HTML.
The "why" to talk through:
When validation passes, handleSubmit() builds a sig object with all the form data, then passes it to addTableRow(). Inside that function, the code uses document.createElement() to build each piece — a <tr>, then individual <td> elements for Name, City, Type, and the "more" link. Each <td> gets its text set with .textContent, then gets appended to the row with appendChild(). Finally the row gets appended to the <tbody>. No page reload — the DOM updates instantly. The "more" link also gets an event listener attached right at this moment, with a closure over the sig object so it always opens the modal for that specific row's data.
Alternative technique to research:

"Instead of createElement + appendChild, you could build the entire row as an HTML string and inject it using innerHTML or insertAdjacentHTML()."

For example:
jstbody.insertAdjacentHTML('beforeend', `<tr><td>${sig.name}</td>...</tr>`);
Justify your choice:
createElement is safer — innerHTML can be a security risk if any user input contains HTML characters (imagine someone typing <script> in the Name field). It's also easier to attach event listeners to specific elements when you have a direct reference to them, which you need for the "more" link closure.
Demo trick — live fix:
In addTableRow(), temporarily comment out the tbody.appendChild(tr) line. Submit a valid form — nothing appears in the table. Then uncomment it, resubmit — row appears. Simple and makes the point that appendChild is the actual moment the DOM updates.

Topic C — Bootstrap Modal (5 pts)
What to show on screen:
Show the modal HTML in Petition2.html (the <div class="modal fade" id="detailModal"> block), then show openModal() in Petition2.js.
The "why" to talk through:
The modal markup lives in the HTML the whole time — Bootstrap keeps it hidden until triggered. When a "more »" link is clicked, it calls openModal(sig) with that row's specific sig object (this works because of the closure in addTableRow — each link "remembers" its own data). Inside openModal(), the code sets the modal title, then loops through an array of label/value pairs — name, email, city, state, signer type, any conditional fields, and comment — and dynamically builds table rows in #modalDetailTable. City and state get .toUpperCase() called on them, which is why they appear in all caps. Then new bootstrap.Modal(modalEl).show() is called — that's Bootstrap's JS API to trigger the display. No display toggling needed — Bootstrap handles all of that internally.
The key thing that makes each "more" link show the right data is the closure. When addTableRow() runs, the event listener captures the sig variable at that moment. Each row gets its own listener with its own sig — so clicking Alice's link always opens Alice's data, never Bob's.
